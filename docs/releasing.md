# 发布手册

本文定义 Windows x64 便携 ZIP 的正式发布流程。自动发布只负责 GitHub Release，不包含安装器、应用内自动更新或正式代码签名。

## 一次性配置

1. 在 GitHub 仓库的 **Settings → Environments** 创建 `release` 环境。
2. 配置维护者为 Required reviewer，并将可部署分支限制为 `main`。当前由维护者兼任发布触发者和最终审批人，不强制双人审批。**必须先完成这一项**：如果引用的环境不存在，GitHub 可能自动创建没有审批保护的环境。
3. 建议配置 `v*` 标签保护或仓库规则集，只允许发布流程创建和管理发布标签。`concurrency` 只阻止本工作流并行，无法阻止另一个有写权限的流程在审批与发布之间移动或删除标签。
4. 不需要添加模型密钥或签名凭据。工作流使用 GitHub 自动提供的 `GITHUB_TOKEN`；构建任务只有读取权限，发布任务只在 `release` 环境中获得写入权限。

不要绕过环境审批，也不要给普通检查工作流增加发布写权限。

## 1. 准备发布 PR

1. 确认所有产品改动已经合并到 `main`，本次只发布 `main` 已包含的提交。
2. 在普通 PR 中更新 `package.json` 和 `package-lock.json` 的根版本。可使用 `npm version <版本> --no-git-tag-version`，不要在此时创建标签。
3. 在 `CHANGELOG.md` 添加唯一且非空的正式版本章节，格式为 `## [X.Y.Z] - YYYY-MM-DD`。只支持正式版，不使用 Alpha、Beta、RC 或其他后缀。
4. 检查 README 和发布说明没有承诺尚未验证的能力。当前发行版未正式签名，发布说明必须保留相应提示。
5. 审查并合并发布 PR。版本、锁文件、标签和 Release 由工作流再次核对；已有版本、标签或 Release 会直接阻断，绝不覆盖。

## 2. 构建候选包

1. 打开 Actions 的 **发布** 工作流，在 `main` 分支选择 **Run workflow**。
2. 输入不含 `v` 的版本。提交 SHA 留空时取最新 `main`；重新发布历史提交时填写完整 SHA，该提交仍必须已经包含在 `main` 中。
3. 工作流会检查版本和发布说明，运行公开内容检查、自动化测试、全部隐藏界面与功能专项、原生构建、打包及冻结便携包验证。版本门禁分页读取全部 Release，只取非草稿、非预发布版本的标签，再按语义化版本比较；新版本必须高于当前最新正式版本，不能补发更低的旧版本。
4. 成功后下载 `PickGloss-<版本>-candidate` Artifact。候选包只保留 14 天，此时尚未创建正式标签或公开 Release。

候选 Artifact 中的 `release.json`、候选清单和发布说明用于发布核验；公开 Release 只上传 ZIP、`release-checksum.json` 和 `SHA256SUMS.txt`。

## 3. 人工验收

审批前必须完成基础真机冒烟检查，并确认检查的是刚下载的候选包。先核对 ZIP 的 SHA-256：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath <候选ZIP>
Get-Content -LiteralPath <SHA256SUMS.txt>
```

每次发布至少检查：

- 在专用验收环境启动完整便携目录，使用虚构文本完成一次真实解释和追问，并确认会话能够保存、重新打开。
- 从自有测试窗口实际划词，确认划词入口、解释窗口和返回原软件的基本交互。
- 对固定中英文测试图片实际框选，确认本机 OCR、覆盖译文、对照和原图切换；使用自行配置的测试服务，记录服务及费用边界。
- 核对 Windows 版本、显示缩放、屏幕数量、是否正式签名及仍未覆盖的能力，不把绿色 CI 当作真机验收。

候选包内 `README.txt` 的隔离模式适合不接触日常数据的自动检查，但它会禁用系统划词监听等真实桌面能力，不能代替上述人工冒烟。真实桌面验收应使用专用测试数据，避免读取或改动日常会话与密钥。

改动涉及原生助手、窗口外观、截图来源、多显示器、OCR 或打包时，必须追加对应专项。具体入口及证据边界见 `docs/engineering-verification.md`；其他 DPI、机器和人工观感不能由隐藏界面测试替代。

## 4. 审批与公开

1. 确认候选包验收完成后，在 Actions 中审批等待中的 `release` 环境部署。
2. 审批通过后，发布任务重新 fetch 当前 `main`，并确认候选提交仍是 `FETCH_HEAD` 的祖先。审批等待期间即使 `main` 已有新提交，只要候选提交仍在主线历史中就可继续；若主线改写导致候选提交不再包含于 `main`，发布必须停止。
3. 发布任务重新核对冻结资产和版本碰撞，然后通过 Git refs API 原子创建 `vX.Y.Z` 标签，再用 `--verify-tag` 创建正式 Release，防止标签被并发操作替换。
4. 发布的是候选 Artifact 中的同一个 ZIP，不会重新构建或手工修改资产。
5. 工作流随后核验标签指向，重新下载三个公开资产，并逐字节比较候选文件。只有这些检查全部成功，整个发布工作流才算成功。

## 失败与问题版本

- 审批前失败不会产生正式标签或 Release；修复原因后可以重新运行，版本仍必须未被使用。
- 标签创建成功后立即回读并确认目标。若 Release 创建失败且确认 Release 不存在，流程只清理仍指向选定提交的本次标签；标签已被移动、无法确认状态或 Release 可能已经公开时保留现场，转为人工处理。
- 若标签创建请求超时但服务端实际已经创建，下一次发布前置检查会识别该状态并安全停止；需要人工确认这是本次未完成流程还是其他写操作后再处理。
- Release 创建后任一核验失败会保留失败状态并提醒人工处理。不得自动删除、覆盖或重发相同版本，应先检查 GitHub 上的实际状态。
- 已公开版本发现严重问题时，采用修复并发布新补丁版的前进策略。必要时人工标注旧 Release，不由 CD 自动撤下。
- 上传命令成功不等于发布核验成功；最终应以重新下载核验结果为准。
