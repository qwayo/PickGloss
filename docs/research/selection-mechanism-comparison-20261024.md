# 豆包与 PickGloss 划词机制核对及讨论

日期：2026-10-24。

本记录核对用户提供的《豆包划词机制与 PickGloss 差异调研_2026-10-23.md》，用于讨论可借鉴的机制。两轮讨论的六项推荐均已由用户确认。本文记录现状事实、证据边界、已确认的产品行为及后续验证范围，不代表已经完成功能改造。

核对起点为 PickGloss `7b78d51`、版本 `0.1.13`，讨论分支为 `codex/selection-discussion`。讨论开始时 `selection-worker.cjs`、`ContextProbe.cs`、`desktop.cjs` 的 SHA-256 均与原调研一致，因此下述现状修正来自对同一份代码的重新解释，并非版本变化。后续实施已开始，以下机制核对保留为变更前快照，实施与验证结果另行记录。

## 当前机制

### PickGloss

```text
底层 selection-hook：UIA → MSAA/IAccessible → 可选剪贴板
                         │                  PickGloss 已禁用剪贴板
                         ↓
有文本事件：hook 文本 → ContextProbe 用 UIA 复核选区并尝试读取上下文
手势后备：按下 → 预热助手取得本次基线 → ready → 松开 → UIA 验证选区变化
                         ↓
选定内容有效 → 显示划词入口 → 用户点击 → 创建解释会话
```

两条采集分支不能把每一步都相加，描述成每次划词必经的完整串行链路。

- **底层已经支持 MSAA。** `node_modules/selection-hook/src/windows/core/engine.cc:146–207` 实现 UIA、MSAA、可选剪贴板的顺序回退。`FOCUSCTL` 则是已移除方法的兼容数值，不能当成另一条现用取词路径。
- **外层仍要求 UIA 复核。** `src/windows/selection-worker.cjs:62–78` 不会直接发布 hook 上报的文字；`src/windows/ContextProbe.cs:107–124` 要求真实 UIA 选区与该文字一致。因此底层 MSAA 取词成功，不代表最终一定能显示入口。
- **选定内容与上下文已经分开判断。** `ContextProbe.cs:153–176` 在段落不可靠、跨段或超过 6000 字符时，可返回 `valid=true`、非空选定内容、空上下文及缺失原因。原调研把这些情况概括为拒绝整次划词，表述过强。
- **语境解释仍需要上下文。** `src/core/provider.cjs:74` 在缺失上下文时拒绝语境解释；现有 README 已说明可以独立释义或手动补充上下文。允许显示入口不等于允许把未知上下文交给模型猜测。
- **手势基线有时间约束。** `selection-worker.cjs:80–109` 要求松开前已收到基线 `ready`，并检查位移、持续时间及超时。松开后再采到的状态不能直接冒充划词前基线。该约束只属于手势后备分支。
- **助手已有预热，入口窗口尚未提前创建。** `selection-worker.cjs:16–60,94–108` 与 `ContextProbe.cs:83–95` 预热并交接待用助手；正常文本事件另行启动活动探针。`src/windows/desktop.cjs:387–407` 首次显示时创建划词入口，后续复用；首次加载完成前还要等待页面就绪。
- **点击才建立解释会话。** `desktop.cjs:606–610` 和 `src/main.cjs:347–350` 表明，入口显示与解释会话建立是两个时点。若以后分阶段返回材料，需明确用户在上下文返回前点击时采用哪份材料。

### 豆包

原调研有网页脚本、原生日志和 DLL 字符串三类依据，证明强度应分别保留。

- 当前本机 `content.js` 仍存在 `openNativeSelection`，把文本、URL、段落及矩形交给 `popupTextPickerToolbar`，场景字段为 `client_browser_webpage`。这是豆包有网页内桥接路径的直接证据，不能外推为所有 Chrome、Edge 或任意 Electron 应用都会使用该路径。
- 用户补充：未安装浏览器扩展时，豆包仍能在网页划词后快速显示按钮。这是用户实际体验反馈，本轮尚未受控复测。该场景不能归因于已经发现的网页脚本；原生桌面取词是独立路线，浏览器扩展不是快速显示入口的必要条件。
- 原调研记录的 UIA、WPS/Excel、剪贴板和工具条复用痕迹，可作为候选机制的线索。DLL 字符串不能独立证明全部回退顺序、实际命中频率或应用覆盖率。
- 本轮发现本机豆包资源大小、修改时间已不同于原快照。本轮仅补核网页桥接片段，没有重新还原原生实现或复跑原日志实验。
- 原调研的若干耗时从鼠标按下计算到选区日志或工具条更新，包含用户操作时间，也没有证明窗口已经可见。它们不能直接作为松手后入口延迟，亦不能证明豆包没有基线等待策略。
- 尚无受控对照足以判定两者的字符准确率、实际成功率或延迟分布优劣。

## 可借鉴的机制与使用条件

| 机制 | PickGloss 的现状 | 可借鉴部分与限制 |
| --- | --- | --- |
| 隐藏窗口预热及复用 | 已复用，首次才建窗 | 可评估提前创建并完成入口页面加载；收益主要在首次显示，不能解释所有连续划词延迟 |
| 按取词来源分别验证 | 底层多来源，外层统一依赖 UIA | 值得研究让每条路径自行证明本次选区、来源及取消状态；不能仅凭拿到字符串就视为可信 |
| 已验证文字先显示，上下文后补 | 已允许没有上下文，但当前单次结果仍等待段落读取尝试 | 可以讨论拆分返回时机；须先完成选定内容校验，防止迟到段落覆盖新选区，并明确提前点击的行为 |
| 网页 DOM 取词 | 当前没有面向外部浏览器的页面桥 | Chrome/Edge 可通过扩展及本机通信实现；不是纯桌面端增加一次 getSelection 调用就能覆盖所有应用 |
| 应用专用取词 | 当前没有在这条采集链路中接入 Office/WPS 专用读取 | 应先选定确实失败的目标应用，再核查其公开接口、可获得的选区证明和运行代价 |
| 剪贴板回退 | 库已实现，PickGloss 明确关闭 | 不需要重新复制豆包机制；是否接纳是独立产品选择，涉及原有内容、并发复制和应用副作用，不能简单开开关就声称覆盖问题解决 |
| 快松手支持 | 手势后备要求松开前收到基线 | 可测量助手交接和基线获取耗时；不能把松开后补采的基线视为等价优化 |

网页 DOM 路径的关键条件是能够进入目标页面并可信地把结果送回桌面应用。Chrome 的内容脚本运行于授权页面，可通过扩展内部消息转发给本机通信宿主；宿主还需要注册。iframe 需要相应的匹配与框架处理，不能一概称为无法支持，也不能默认已经支持。[内容脚本文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)、[本机通信文档](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)。

从 Electron `webContents` 文档的应用内实例模型推断，PickGloss 不能仅凭自身是 Electron 应用，就直接读取其他独立 Electron 软件的 DOM。第三方软件需要其自身配合或另一种明确的连接条件。[Electron 文档](https://www.electronjs.org/docs/latest/api/web-contents)。

仓库此前的 [桌面入口跟随调研](desktop-selection-follow.md) 已讨论无扩展调试桥，但其前提是开启浏览器调试连接；该文中的历史版本和固定样本结果不能当作本轮复测。本次讨论的是取词及入口出现，不自动重启滚动跟随设计。

## 研究顺序

先测出已有桌面路径的延迟构成和失败原因，再选择优化对象。隐藏入口预热是范围较小的候选；若反复划词也慢，应继续查看文本事件分支的助手启动、UIA 复核及段落读取，而不能只归因于首次建窗。

若要扩展覆盖范围，应重点讨论不同来源如何证明本次选区。已有 MSAA 能力被后续 UIA 要求限制的事实，比新增一个同样的底层接口更值得调查。网页扩展则适合作为单独评估的增强路线，其价值取决于用户是否接受安装和授权条件。

可借鉴流程、能力分工和降级方式。豆包 DLL、打包脚本及私有桥接接口不作为 PickGloss 的运行依赖；本轮未复制任何豆包文件。

## 已确认的产品原则

用户在两轮讨论中均表示全部按推荐处理，确认以下原则：

1. 首先改善现有桌面路径的连续划词成功率和松手后延迟，再扩展新应用。
2. Chrome/Edge 扩展可以作为可选增强；桌面基础功能保持独立运行。结合用户补充，优先研究不安装扩展的桌面路径。
3. 选定内容已经验证后，可以先显示入口、后台补上下文；文字本身未验证时继续等待。
4. 本轮继续关闭自动复制式剪贴板回退，后续按明确的应用覆盖缺口单独讨论。
5. 混合选区中可靠可取的文字可以解释；正文与命令保留顺序和换行，Unicode 表情保留；独立图片不自动进行文字识别，纯图片继续通过截图框选使用。
6. 上下文尚未返回时点击划词入口，立即打开解释窗口并展示已验证的选定内容，继续获取上下文。独立释义可使用已验证文字；语境解释等待上下文就绪或由用户手动补充。

当前没有未回答的产品取舍。来源验证方式、失败原因及速度改善幅度由后续复现和测量确定，不把未经验证的机制推断写成既定实现。当前未形成难以撤销的重大架构取舍，因此不创建 ADR；已确认的“混合选区”术语已写入根目录 GLOSSARY。

## 新增反馈：跨内容块或文字与图片混选时缺少入口

用户已明确选择问题类型：文字与图片或表情一起选中时，划词入口不出现。不能把该反馈写成入口点击失效，也不能推断为之后所有纯文字划词失效。

用户进一步给出两类场景：

- Codex 桌面软件中，同时拖选 AI 输出正文与下方执行的命令，不出现划词入口。
- 视频网站中，同时拖选视频标题与封面，不出现划词入口。

因此反馈范围包含跨内容块选择，不能全部归为内联图片或表情问题，也不能预先认定两类场景同因。本轮尚未复现，不把字符清洗、UIA 文本不一致、图片节点或矩形问题预先写成原因。构建对照应分别覆盖单块文字、正文加命令块、文字加 Unicode 表情、文字加内联图片、标题加封面及纯图片；先确认失败场景，再核对文本采集与入口显示的边界。

已确认的处理行为是：混合选区中可靠可取的文字可用于解释；文字中的 Unicode 表情属于文字；独立图片不自动转为文字或触发截图解释。正文与命令块、标题与封面是分别验证的场景。

复现设施已只读定位：`scripts/check-context-probe.cjs --chromium` 及 `tests/fixtures/context-probe-chromium.cjs` 可验证自建输入控件与 Unicode 表情，但现有夹具没有上述跨块 HTML 与标题封面对照，也没有覆盖全局 hook 到真实划词入口的完整链路。`scripts/check-selection-gesture.cjs` 的图标对象用例不能替代文字与封面的混合选区。现有用例不足以宣布用户问题已复现或已修复，后续应建立能实际捕获此类缺少入口的对照后再判断原因。

## 分阶段返回材料的行为边界

- 划词入口只对应已验证的选定内容。图片、上下文缺失或段落不可靠，不能直接充当文字本身无效的判据；文字来源和本次选择关系仍需验证。
- 点击入口后，解释会话保存本次选定内容。上下文仍在获取时，解释窗口及时打开并显示等待状态；取得上下文后再提供语境解释。
- 缺失上下文时保留独立释义和手动补充上下文的现有选择，不自动切换解释模式，也不因后台补齐上下文自动发起模型请求。
- 迟到材料只能写入它所属的选定内容及解释会话；新的划词不能被旧材料覆盖。用户手动补充或编辑的上下文优先于随后到达的自动材料。
- 继续使用现有选定内容 12000 字符、上下文 6000 字符上限。取得文字、取得上下文和最终解释分别报告可用状态。

## 后续验证与实现范围

首先为两类混合选区建立能捕获缺少入口的复现，记录底层事件、选定内容验证结果及入口显示时点。复现应尽可能覆盖真实全局采集链路；只通过直接调用探针的夹具不足以宣布桌面问题已经解决。

随后测量冷启动首次划词和连续划词，区分正常文本事件与手势后备，判断入口页面预热、活动助手启动及段落读取各自的贡献。确认瓶颈后，再确定助手复用、分阶段返回和不同来源的验证实现；保留遇到失效提供方时可以超时终止的隔离能力。

本轮实现范围以不安装浏览器扩展的桌面路径及用户提供的拖选场景为主。浏览器扩展、Office/WPS 专用适配和剪贴板回退留作独立增强；本轮讨论不承诺已经支持这些新增来源。

验收需覆盖纯文字、正文与命令块、文字与 Unicode 表情、标题与封面、纯图片、上下文缺失时点击入口，以及连续更换选区后迟到材料的归属。统计松手后入口延迟分布时，同时记录失败率、误触发率和文字一致性，避免仅统计成功样本后得出片面的提速结论。

## 验证边界

上述机制核对对应讨论阶段的文件、源码及官方文档阅读。当时没有运行程序、测试、打包或原生桌面性能实验。后续已按用户确认进入实施；实施期间的自动化、原生对照和剩余限制记录于本机验证文档 `docs/verification/划词与AI服务实施验证-20261024.md`，不回写成讨论阶段已经证明的结论。

若进入后续验证，应分别记录冷启动首次显示、连续划词、快速拖选、原选区未变、连续替换选区，并区分 hook 文本分支与手势后备分支。以松手到可操作入口的时间分布、失败率、误触发率和选定内容一致性评估体验；上下文可用率另行记录。

仓库已有 `scripts/selection-entry-timer.cs` 与 `scripts/summarize-selection-entry.cjs` 可作测量起点。现有计时器以窗口和 UIA 按钮可观察状态作为指标，仍需人工核对选定内容和实际视觉体验，不能把该观察时点直接视为所有环境下的最终绘制时刻。
